# Kitchen Display (จอครัว คิวออเดอร์) — Dev Handoff

ต่อยอดจากระบบ jinko-order (`/admin`). ดีไซน์ต้นแบบ: Design artifact "จอครัว คิวออเดอร์" (ไฟล์ `Main.dc.html`). ข้อมูลในต้นแบบเป็นตัวอย่าง ไม่ใช่ข้อมูลจริง

## 1. เป้าหมาย
- หน้าจอครัวแสดงคิวออเดอร์ที่ยังไม่ทำ เรียงตามเวลารอ อ่านง่ายจากระยะไกล
- พนักงานครัวติ๊กเสร็จ/ยกเลิกได้ทีละเมนู
- ใช้ได้ทุกขนาดจอ (แท็บเล็ตแนวนอนเป็นหลัก, ทีวี, มือถือ)
- ภาษา UI: ไทย

## 2. ข้อมูลที่หน้าจอต้องใช้ (ต้องให้ dev ยืนยันกับฐานข้อมูลเดิม)
จาก `/admin` ที่มีอยู่แล้วเห็นฟิลด์: เลขที่บิล, โต๊ะ, รายการ/จำนวน, หมวดรายการ (ใช้กับเครื่องพิมพ์ครัว), เวลา, หมายเหตุลูกค้า. **ยังไม่ได้ตรวจ schema จริง** ด้านล่างเป็นโครงที่หน้าจอต้องการ

```
Order   { id, billNo, table, createdAt, status? }
Item    { id, orderId, name, qty, note?, status: 'pending'|'done'|'cancelled', isAddOn: boolean, addedAt?, doneAt? }
```
- เวลารอ = `now - order.createdAt` (คำนวณฝั่ง client ทุก 1 วินาที)
- `Order` เสร็จเมื่อทุก Item ไม่เป็น `pending`
- ต้องมีฟิลด์สถานะรายเมนู (ถ้าระบบเดิมเก็บสถานะแค่ระดับออเดอร์ ต้องเพิ่ม)
- ออเดอร์ที่ "สั่งเพิ่ม" (ปุ่ม + สั่งเพิ่ม ใน admin) ต้องเข้าเป็น Item ใหม่ในออเดอร์เดิมของโต๊ะนั้น โดยตั้ง `isAddOn = true` (ต้องยืนยันกับ dev ว่าระบบเดิมแยกรายการสั่งเพิ่มได้ไหม)

## 3. เลย์เอาต์
- **ซ้าย "รอทำ"**: ตารางการ์ด (ตั๋ว) ขนาดเท่ากัน สูงคงที่ ~430px, กว้างขั้นต่ำ 290px, จำนวนคอลัมน์ปรับตามจอ (`repeat(auto-fill, minmax(290px, 1fr))`)
- **ขวา "เสร็จแล้ว"**: กว้าง `clamp(220px, 20vw, 300px)`; จอแคบกว่า 820px ย้ายลงใต้ (สูงสุด 32vh)
- **ไม่แบ่งหน้า**: เลื่อนลงในพื้นที่ "รอทำ"; การ์ดแถวถัดไปโผล่บางส่วนเป็นสัญญาณว่ามีคิวต่อ
- **แถบบน**: ชื่อหน้าจอ, จำนวนโต๊ะรอทำ, นาฬิกา (HH:mm)
- ไม่มีตัวกรองหมวด, ไม่มีตัวนับ "เสร็จแล้ว" ที่แถบบน

## 4. การ์ด (ตั๋ว)
- หัวการ์ด: `โต๊ะ N`, `#เลขบิล`, `เสร็จ x/y`, เวลารอ `mm:ss`, ป้ายสถานะ
- ตัวการ์ด: รายการเมนู 1 แถว/เมนู: [วงกลมเสร็จ] [จำนวน×] [ชื่อ + หมายเหตุสีส้ม]
- ท้ายการ์ด: ปุ่ม "เสร็จทั้งใบ (n)" แสดงเมื่อมีเมนูค้าง > 1
- **ออเดอร์ยาว**: ตัดเป็นหลายใบ ใบละ **6 รายการ** (ปรับได้) เรียงต่อกัน หัวการ์ดมีป้าย `ใบ 1/2`; เวลาและสีหัวการ์ดเหมือนกันทุกใบของโต๊ะเดียวกัน
- เรียงลำดับ: ด่วนก่อน → ลำดับที่ลากไว้ → เวลารอมากสุด (ดูหัวข้อ "ด่วน / ลากการ์ด")

### สัญลักษณ์ "สั่งเพิ่ม"
- รายการที่ `isAddOn = true`: ป้ายม่วง `+ สั่งเพิ่ม` ท้ายแถว + พื้นแถวม่วงอ่อน `#f4eefc` (ป้ายม่วง `#6b3fa0` ตัวอักษรขาว)
- หัวการ์ด: ป้าย `+ สั่งเพิ่ม` ใต้เลขบิล ถ้าใบนั้นมีรายการสั่งเพิ่มที่ยังไม่ถูกยกเลิก
- สีม่วงสงวนไว้สำหรับ "สั่งเพิ่ม" เท่านั้น ไม่ปนกับสีสถานะเวลา
- ป้ายหายเมื่อรายการนั้นถูกยกเลิก
- ข้อควรตัดสินใจ: เมื่อมีสั่งเพิ่มเข้ามา ควรให้ออเดอร์กลับมาเป็นสถานะ "ใหม่" (ฟ้า) ชั่วคราวหรือไม่ — ต้นแบบยังไม่ทำ

### ด่วน / ลากการ์ดเพื่อขึ้นคิวก่อน
ใช้เมื่อโต๊ะที่สั่งเพิ่มเล็กน้อยหรือลูกค้ากำลังจะลุกกลับ ต้องการให้ครัวทำก่อน
- **ปุ่ม "ด่วน"** (ท้ายการ์ด): สลับสถานะด่วน; ออเดอร์ด่วนอยู่ลำดับแรกเสมอ มีแถบดำ "ด่วน · ทำก่อน" บนการ์ดทุกใบของโต๊ะนั้น; กดซ้ำ ("เลิกด่วน") เพื่อกลับไปเรียงตามเวลา
- **ลากการ์ด**: จับที่ปุ่ม `⋮⋮` มุมซ้ายหัวการ์ด ลากไปวางทับการ์ดอื่น → ออเดอร์นั้นแทรกก่อนการ์ดเป้าหมาย (ย้ายทั้งโต๊ะ ไม่ใช่เฉพาะใบเดียว); ระหว่างลากการ์ดลอยขึ้นพร้อมเงา และการ์ดเป้าหมายมีกรอบประ; ถ้าวางก่อนออเดอร์ด่วน ออเดอร์นั้นกลายเป็นด่วนด้วย
- ลำดับการเรียง: ด่วน → ลำดับที่ลากไว้ (rank) → เวลารอมากสุด
- ต้องเก็บ `rush` และ `rank` ในฐานข้อมูล/สถานะที่ซิงก์ทุกจอครัว (ไม่ใช่แค่ในเครื่อง)
- ปุ่มลากใช้ `touch-action: none` เพื่อไม่ชนกับการเลื่อนหน้า — ต้องทดสอบบนแท็บเล็ตจริง
- ไม่มีการบังคับขึ้นด่วนอัตโนมัติเมื่อมีสั่งเพิ่ม (ยังเป็นการตัดสินใจของพนักงาน)

## 5. สถานะตามเวลารอ (ค่ากำหนดโดยผู้ใช้)
| เวลารอ | ป้าย | หัวการ์ด | อนิเมชัน |
|---|---|---|---|
| < 15 นาที | ปกติ | เทาอ่อน `#e8edf1` ตัวอักษรเข้ม | ไม่มี |
| ≥ 15 นาที | ช้า | เหลือง `#f5b301` | ไม่มี |
| ≥ 20 นาที | ช้ามาก! | แดง `#c9302c` ตัวอักษรขาว | กะพริบ (opacity) |
| ออเดอร์ใหม่ (< 90 วินาทีหลังเข้า) | ใหม่ | ฟ้า `#1f78d1` ตัวอักษรขาว | เรืองแสงกะพริบ |

- เกณฑ์ 15/20 นาทีต้องเป็นค่าตั้งได้ (config / หน้า admin)
- สถานะไม่พึ่งสีอย่างเดียว มีป้ายข้อความเสมอ (accessibility)
- ควรเคารพ `prefers-reduced-motion` (ปิดอนิเมชันกะพริบ)

## 6. การกระทำของผู้ใช้
| การกระทำ | ผลลัพธ์ |
|---|---|
| แตะวงกลมหน้ารายการ | `pending → done`; แตะซ้ำ = `done → pending` |
| ปัดรายการไปทางซ้าย | เผยปุ่มแดง "ยกเลิก" (กว้าง 80px); ปัดขวากลับเพื่อซ่อน |
| แตะ "ยกเลิก" | `pending → cancelled` (ไม่มีหน้าต่างยืนยัน เพราะการปัดเป็นการยืนยันอยู่แล้ว) |
| แตะ "คืน" ที่รายการยกเลิก | `cancelled → pending` |
| แตะ "เสร็จทั้งใบ" | ทุก `pending` ในใบนั้น → `done` |
| ทุกเมนูไม่ค้าง | ออเดอร์ย้ายไปคอลัมน์ "เสร็จแล้ว" พร้อมเวลาที่ใช้ |
| แตะ "ย้ายกลับ" (คอลัมน์เสร็จ) | ทุกรายการ → `pending` |

- รายการ done: ติ๊กเขียว ชื่อเทา; cancelled: ขีดฆ่า + ป้ายแดง "ยกเลิกแล้ว"
- ปุ่มต้องกดง่ายด้วยนิ้ว (เป้าแตะ ≥ 40px; ปุ่มหลักใน footer ≥ 48px)
- การสั่งงานทุกครั้งต้องเขียนกลับฐานข้อมูล (ต้นแบบยังไม่เชื่อมระบบ)

## 7. Realtime และความถูกต้อง
- ออเดอร์ใหม่ต้องขึ้นเองโดยไม่รีเฟรช (WebSocket / Supabase Realtime / SSE / polling สั้น — dev เลือกตามระบบเดิม)
- ถ้าหลายจอครัวเปิดพร้อมกัน สถานะรายเมนูต้องซิงก์ตรงกัน และกันการกดซ้ำชน (last-write-wins หรือ optimistic + reconcile)
- ปุ่ม "รีเฟรช" แบบ manual เป็น fallback ได้
- เวลารอใช้ `createdAt` จากเซิร์ฟเวอร์ ไม่ใช่เวลาเครื่องจอ (กันนาฬิกาเพี้ยน)
- หน้าจอควรกันจอดับ (Wake Lock API) เมื่อใช้งานเป็นจอครัว

## 8. สไตล์ (จากต้นแบบ)
- พื้นขาว `#ffffff`, แถบบน `#f3f5f7`, เส้นขอบ `#dfe3e7`, ตัวอักษร `#1b1f23`
- เขียว (เสร็จ) `#178a4c`, แดง (ยกเลิก/ช้ามาก) `#c9302c`, น้ำเงินจำนวน `#1f5fa8`, โน้ตลูกค้า `#b3430a`
- ฟอนต์: Noto Sans Thai (400/600/800)
- ขนาดตัวอักษรหลัก: โต๊ะ 30px, เวลา 26px, ชื่อเมนู 19px, โน้ต 15px
- ข้อจำกัดที่ทราบ: ขนาดตัวอักษรคงที่ทุกจอ ถ้าใช้กับทีวีไกล ๆ ควรทำสเกลตามความกว้างจอ

## 9. สิ่งที่ต้นแบบยังไม่ได้ทำ / ต้องยืนยัน
- ยังไม่ได้ทดสอบการปัดบนแท็บเล็ตจริง (ใช้ Pointer Events; ใช้ `touch-action: pan-y`) — ต้องทดสอบบนอุปกรณ์จริง
- ยังไม่ได้ตรวจ schema/API ของระบบเดิม ต้องให้ dev ยืนยันโครงข้อมูลข้อ 2
- เสียงแจ้งเตือนออเดอร์ใหม่: ไม่ได้ทำ (เสนอเป็นขั้นต่อไป)
- การพิมพ์ใบสั่งครัวผ่านเครื่องพิมพ์ (ตั้งค่าอยู่ใน `/admin` อยู่แล้ว) เป็นระบบแยก ไม่เกี่ยวกับหน้าจอนี้
- สิทธิ์การเข้าถึงหน้าจอครัว (ล็อกอิน/PIN) ยังไม่ได้กำหนด

# ข้อกำหนดที่ยึดแทน spec ข้างบน (ตัดสินใจโดยเจ้าของงาน)
เมื่อขัดกับข้อความด้านบน ให้ยึดหัวข้อนี้

1. **กรองหมวด**: ไม่แสดงหมวด "เครื่องดื่ม" (หมวดเดียว) กรองฝั่งเซิร์ฟเวอร์ ใช้ฟิลด์ `category` เดิม ชื่อหมวดเป็น config
   - มีแต่เครื่องดื่ม = ไม่แสดงเลย | ผสม = แสดงเฉพาะที่ไม่ใช่เครื่องดื่ม
   - "เสร็จ x/y" และการย้ายไป "เสร็จแล้ว" นับเฉพาะรายการที่แสดง | สั่งเพิ่มใช้กฎเดียวกัน
2. **เกณฑ์เวลารอ (config ทั้งหมด)**: < 15 นาที = ปกติ (เทา) | 15:00–24:59 = ช้า (เหลือง ไม่กะพริบ) | ≥ 25 นาที = ช้ามาก! (แดง + ป้าย + กะพริบ) | ไม่มีเกณฑ์ 20 นาที (ต้นแบบใช้ 20 ให้แก้เป็น 25)
3. **สั่งเพิ่ม**: เป็น Item ใหม่ (`isAddOn`) ในการ์ดเดิม
   - เวลารอใช้ `createdAt` ของออเดอร์เดิม ไม่นับใหม่
   - เมื่อมีสั่งเพิ่ม การ์ดขึ้นสถานะ "ใหม่" (ฟ้า เรืองแสง) 90 วินาทีนับจาก `addedAt` แล้วกลับสีตามเวลารอเดิม
   - ถ้าออเดอร์อยู่ใน "เสร็จแล้ว" แล้วมีสั่งเพิ่ม ให้ย้ายกลับ "รอทำ"
4. **ด่วน/ลากการ์ด**: ทำตามหัวข้อ "ด่วน / ลากการ์ด" ครบ
   - ลำดับ: ด่วน → rank → เวลารอมากสุด | rank ชนะเวลารอเสมอ
   - การ์ดใหม่ที่ไม่เคยลากต่อท้ายกลุ่ม rank เรียงตามเวลารอ
   - เก็บ `rush`/`rank` ในฐานข้อมูล ซิงก์ทุกจอ | ลากย้ายทั้งโต๊ะ ไม่กระทบเวลา/สถานะอื่น | ไม่ตั้งด่วนอัตโนมัติเมื่อมีสั่งเพิ่ม
5. **PWA**: fullscreen แนวนอน เปิดเข้า `/kitchen` | Wake Lock (ขอใหม่เมื่อกลับมา) + เชื่อมต่อใหม่อัตโนมัติ + แสดง "ออฟไลน์" ชัดเจน (ห้ามแสดงข้อมูลเก่าโดยไม่บอก) | ไม่มี PIN/ล็อกอิน
6. **APK Android**: ยังไม่ทำรอบนี้

## กฎเหล็ก
- ห้ามเปลี่ยนดีไซน์ / เพิ่มฟีเจอร์นอก spec / แตะ `/admin` และระบบพิมพ์
- ใช้ API/ฐานข้อมูลเดิม เพิ่มเฉพาะที่จำเป็น (ไม่กระทบข้อมูลเดิม)
- แยกชั้นหน้าตาออกจาก logic | อุปกรณ์: แท็บเล็ต Android แนวนอน

## การตัดสินใจเพิ่มเติม (ยืนยันโดยเจ้าของงาน 2026-10-09)
- "สั่งเพิ่ม" = ออเดอร์ที่เข้ามาเมื่อโต๊ะนั้นเปิดอยู่แล้ว (ออเดอร์แรกวันนี้ที่ยังไม่เคลียร์โต๊ะ) ไม่ว่าสั่งจาก admin หรือลูกค้าสแกน QR
- ชื่อหมวดที่ซ่อน: "เครื่องดื่ม" (config `kitchenConfig.hiddenCategories`)
- เลข `#` บนการ์ด = ลำดับของออเดอร์แรกของโต๊ะเทียบกับออเดอร์ทั้งหมดของวัน (คำนวณตอนอ่าน) ไม่ใช่เลขบิลตอนคิดเงิน เลขอาจข้ามได้ เพราะออเดอร์สั่งเพิ่มก็นับในลำดับด้วย
- โน้ตเป็นระดับออเดอร์ (ทุกออเดอร์มีโน้ตได้) แสดงใต้รายการแรกของแต่ละออเดอร์ในการ์ด ไม่ซ้ำทุกรายการ
- ไม่แก้โค้ดเดิม (`api/orders.js`, `api/table-status.js`, หน้า admin/พิมพ์) "สั่งเพิ่ม" และเลข # คำนวณตอนอ่านใน `/api/kitchen` ส่วนปัญหาออเดอร์เขียนทับกันของระบบเดิม (อ่านทั้งก้อน-เขียนทั้งก้อน) ยังไม่แก้ในรอบนี้ แต่จอครัวเก็บสถานะแยก key จึงไม่เพิ่มความเสี่ยงนี้
